# Проблемы и преимущества

> Документ объединяет назначение подхода и его итоговую ценность: каждое преимущество
> шаблона — прямое следствие конкретной проблемы, которую он решает. Сначала —
> фундаментальная проблема (ИИ как вероятностный исполнитель), затем переход
> «проблема → механизм → преимущество», таксономия отказов дизайн-системы (P1–P9),
> контраст «без подхода / с подходом» и сводная таблица. Механика самих проверок — в
> [02 — Защитные механизмы](02-defense-mechanisms.md), процесс — в
> [03 — Методология разработки](03-methodology.md).

Ценность шаблона определяется не набором библиотек и не числом инструментов, а системой
контроля над их использованием — и тем, какие проблемы разработки эта система снимает.
ИИ-агент пишет основную часть кода под машинно-проверяемыми правилами с первого коммита, а
человек оставляет за собой только неустранимые решения.

---

## 1. Фундаментальная проблема: ИИ — вероятностный исполнитель

Большую часть кода здесь пишет ИИ-агент, а LLM — **вероятностный (стохастический)** автор:
он способен сгенерировать корректный код, но не гарантирует этого. Без ограничений он:

- **галлюцинирует имя токена** — пишет `#3b82f6` или несуществующий `--color-brand`;
- **выдумывает проп** — добавляет в компонент API, которого нет в реальном использовании;
- **импортирует через границу**, которую нельзя пересекать (примитив, тянущий композит в
  обход `index.ts`);
- **без уведомления пропускает состояние** — забывает `empty` / `loading` / `overflow` /
  `error`;
- **подчиняется устаревшему правилу** — следует «авторитетной» инструкции, которая давно
  разошлась с тем, что проверяет CI (дрейф правил).

Защита состоит не в том, чтобы добиться от модели безошибочности (это недостижимо), а в
том, чтобы окружить вероятностного автора детерминированными проверяющими так, что любая
отдельная ошибка обязана пережить _несколько независимых машинных проверок_, прежде чем
попадёт в `main`. Механика этого тезиса разворачивается в
[02 — Защитные механизмы](02-defense-mechanisms.md).

> Почему задачу не решить прозой? Конвенция в README остаётся пожеланием: её легко нарушить
> и невозможно гарантировать. Гейт — это скрипт, выносящий вердикт pass/fail. Текстовые
> договорённости устаревают, гейты — нет.

---

## 2. От проблемы к преимуществу

Преимущества шаблона — не самостоятельные достоинства, а прямые следствия решённых проблем.
Ниже каждая пара дана в порядке «проблема → механизм → преимущество».

### 2.1. Потеря знаний и устаревание конвенций → прослеживаемая неизменяемая история

- **Проблема.** Негласные договорённости существуют лишь в памяти участников и в устаревшем
  README; с уходом людей знание теряется, а новые участники воспроизводят его без понимания
  причин. В случае ИИ-генерированного кода команды как носителя знания может не быть вовсе.
- **Механизм.** Каждое архитектурное решение оформлено как **ADR** (Architecture Decision
  Record) в формате MADR под [`docs/decisions/`](../decisions/). Принятый ADR неизменяем:
  изменение оформляется новой _замещающей_ записью с парными ссылками (`supersedes` /
  `superseded by`), а не правкой на месте. Переход `proposed → accepted` выполняет только
  человек. Постоянная инструкция агента `CLAUDE.md` генерируется из принятого корпуса ADR,
  а не поддерживается вручную, и потому не расходится с решениями; целостность корпуса
  проверяется автоматически (`adr.py lint`).
- **Преимущество.** Причину любого принятого решения можно отследить по соответствующей
  ADR-записи, не восстанавливая мотивацию по истории git или через обращение к команде.
  Введение нового участника или агента сводится к чтению корпуса решений; знание
  зафиксировано в репозитории и не утрачивается при смене состава.

### 2.2. Проза не гарантирует правил → правила-гейты

- **Проблема.** Конвенция, описанная в README, остаётся лишь пожеланием: её легко нарушить
  и невозможно гарантировать.
- **Механизм.** Правило становится **гейтом** — скриптом, который читает реальные файлы,
  проверяет инвариант и завершается с ошибкой при его нарушении. Детерминированные проверки
  `check:*` дополняют `typecheck`, `lint`, `format:check`, измерение покрытия и сканеры
  безопасности. Правило превращают в защитный механизм три свойства:

  | Свойство                  | Что означает                                                              | Чем обеспечено                                     |
  | ------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
  | **Машинно-проверяемо**    | pass/fail определяет скрипт, а не человек, читающий прозу                 | `check:*`, ESLint, `adr.py lint`                   |
  | **Единственный источник** | правило, которое читает агент, тождественно правилу, которое проверяет CI | `gen:tokens`, `gen:types` + проверка на дрейф в CI |
  | **Самоисполняемо**        | гейт доказанно отвергает реального нарушителя                             | `check:gates` (см. 2.5)                            |

- **Преимущество.** Успешный прогон CI означает не формальный просмотр, а подтверждённое
  выполнение заявленного свойства.

### 2.3. «Отмывание знаний» → единственный источник истины

- **Проблема.** Наиболее трудно обнаруживаемый класс ошибок возникает, когда агент следует
  правилу, которое выглядит авторитетным, но незаметно разошлось с тем, что проверяет CI.
- **Механизм.** Всё, чему агент обязан подчиняться, генерируется из единственного
  канонического источника и проверяется на дрейф в CI. Design-токены: слой `@theme` в CSS
  через `gen:tokens` превращается в типизированный union, allowlist для линтера и справочник
  правил для агента (`tokens.agent-rules.md`) — список, который читает агент, и список,
  который проверяет линтер, формируются за один проход по одному источнику. Типы базы данных:
  живая схема Supabase через `gen:types` превращается в `database.types.ts`. CI запускает
  генераторы и завершается с ошибкой при любом расхождении (`git diff`); сгенерированные
  артефакты не редактируются вручную.
- **Преимущество.** Рассинхронизация между знанием агента и требованиями CI технически
  невозможна.

### 2.4. Разный вес гарантий → эшелонированная защита из трёх слоёв

- **Проблема.** Подсказка и блокирующий гейт защищают по-разному, но их легко спутать и
  принять рекомендацию за гарантию.
- **Механизм.** Каждое правило относится ровно к **одному** из трёх слоёв — в зависимости от
  _типа_ требуемой гарантии:
  - **детерминированный** (гейты CI, _блокируют merge_) даёт _точность_: успешный гейт
    подтверждает, что свойство выполнено; именно здесь сосредоточена гарантия;
  - **структурный** (навыки и графы, _предупреждают_) отвечает за _полноту_: снижает частоту
    нарушений внутри рабочего цикла агента, но гарантией не является;
  - **судейский** (человеческие шлюзы) — неустранимое: то, что нельзя свести к скрипту.

  Слои упорядочены по удалённости от момента написания кода: структурные подсказки
  срабатывают, пока агент _принимает решение_; детерминированные гейты — когда он _пишет
  код_ и повторно в _CI_; человек — на границе _merge / accept / promote_.

- **Преимущество.** Для каждого правила заранее определены тип гарантии и точка
  срабатывания, что исключает ложное представление, будто рекомендация защищает так же
  надёжно, как блокирующий гейт.

### 2.5. «Зелёный CI», который ничего не гарантирует → самопроверяемые гейты

- **Проблема.** Гейт, неспособный завершиться ошибкой (забытый assert, отключённое правило),
  неотличим от его отсутствия и создаёт ложную уверенность.
- **Механизм.** `check:gates` (свойство P6) для каждого пользовательского правила внедряет
  заведомого нарушителя (например, сырой hex-цвет в компоненте), запускает гейт и
  подтверждает, что тот отверг нарушителя, восстанавливая исходное состояние в блоке
  `finally`. Мета-проверка выполняется в CI наравне с остальными.
- **Преимущество.** Проверки контролируют сами себя. Гейт, переставший срабатывать
  (постоянно зелёный), будет обнаружен и не сможет дальше маскировать деградацию.

### 2.6. Необратимые действия на скорости ИИ → ведущая роль ИИ при человеческих шлюзах

- **Проблема.** Агент способен быстро выполнить то, что нельзя отменить: принять решение,
  выполнить merge в `main`, выдать секрет, утвердить визуальный бейзлайн.
- **Механизм.** Каждое необратимое или судейское действие закреплено за человеком перечнем,
  а не декларацией (ADR 0046/0047): принятие ADR, настройки репозитория и branch-protection,
  промоут в production, выдача и ротация секретов, правка `constraints.md`, merge в
  `dev`/`main`, утверждение бейзлайна в Chromatic UI. Все ИИ-процессы (ревью PR, триаж CI,
  черновик changelog, обзор безопасности) никогда не являются обязательными проверками — они
  информируют человека, но не заменяют его одобрение; каждый PR требует одобрения человека,
  отличного от автора.
- **Преимущество.** Скорость ИИ сохраняется без потери контроля над действиями, которые
  нельзя отменить.

### 2.7. Расхождение локальной и серверной проверки → воспроизводимость

- **Проблема.** Когда локальный прогон и CI проверяют разное, «у меня всё прошло» ничего не
  значит, а нестабильные тесты маскируются повторными запусками.
- **Механизм.** Один и тот же набор `check:*` выполняется и локально в навыке `pre-pr-gate`,
  и в [`ci.yml`](../../.github/workflows/ci.yml). Глобальные повторные запуски (retry) в CI
  не применяются: нестабильный (flaky) тест явно помещается в карантин — аннотированный skip
  с заведённой задачей и ограничением по времени (ADR 0049). Обязательные статус-проверки
  остаются исключительно детерминированными.
- **Преимущество.** Локальный прогон достоверно предсказывает результат CI; расхождение
  между локальной и серверной проверкой устранено.

### 2.8. Риски цепочки поставок → безопасность, встроенная в гейты

- **Проблема.** Утечка ключа в git, уязвимая транзитивная зависимость, несовместимая
  лицензия, GitHub Action, подменённый по тегу, — риски, которые на ручном ревью
  обнаруживаются ненадёжно.
- **Механизм.** Слой безопасности и целостности (ADR 0056, 0068–0074):
  - **секреты** — блокирующее сканирование `gitleaks` (Layer 1) и совещательный ИИ-обзор
    инвариантов (Layer 2);
  - **SAST** — статический анализ GitHub CodeQL;
  - **уязвимости зависимостей** — `npm audit` как блокирующий шаг (`check:audit`);
  - **закрепление GitHub Actions по SHA** — гейт `check:action-pins`;
  - **лицензии зависимостей** — `check:licenses` с allowlist по SPDX, что существенно для
    шаблона, который наследуют другие проекты;
  - **целостность документации** — проверка ссылок (`links.yml`) и орфографии
    (`check:spelling`);
  - **Conventional Commits** — `check:commits` (commitlint).
- **Преимущество.** Типовые риски обнаруживаются механически, а не за счёт внимательности
  ревьюера.

### 2.9. Дизайн-система как договорённости → дизайн-система как набор проверок

- **Проблема.** Руководство по стилю в прозе не мешает агенту использовать сырой цвет,
  дублировать компонент или пропустить состояние; согласованность приходится поддерживать
  многократным ручным ревью.
- **Механизм.** Governance-слой (ADR 0058–0064) переводит дизайн-систему из договорённостей
  в проверки:
  - **только токены** в компонентах — не допускаются сырые значения цвета и размера,
    инлайн-`style` с сырыми значениями и числовая палитра Tailwind (`check:tokens`);
  - **композиционный граф** (`composedOf`/`usedIn`) сверяется с реальным графом импортов
    средствами dependency-cruiser (`check:graph`), благодаря чему структурное дублирование
    компонента обнаруживается ещё до его создания (`ds:signature`);
  - **покрытие состояний вычитанием** — за основу берётся обязательный набор для архетипа, и
    каждое пропущенное состояние требует явного обоснования; молчание расценивается как
    провал, а не как зачёт;
  - **типизированный `design-intent.ts`** для каждого компонента — API выводится из
    множества `usedIn`, а не назначается произвольно; рассогласование с реальными пропами
    или историями приводит к ошибке CI;
  - **визуальная регрессия** — изменение, которое проходят все функциональные тесты,
    обнаруживается Chromatic (ADR 0043).
- **Преимущество.** Визуальная и структурная согласованность интерфейса поддерживается
  проверками, а не повторным ручным код-ревью.

### 2.10. Прикладной код без стандарта размещения → Feature-Sliced Design с проверяемыми границами

- **Проблема.** Компонентный слой стандартизирован глубоко, а у прикладного — где живут
  доступ к данным, состояние и UI фичи и страница, что их связывает, — стандарта нет. Без
  него код стихийно нарастает под `src/app` и `src/lib`, а направление импортов не
  проверяется ничем. С появлением реальных фич начинается типичная энтропия: фича «профиль»
  обращается к несвязанной фиче «биллинг», UI-компонент импортирует маршрут, возникают
  циклические зависимости — и ничто из этого не ловится ревью на масштабе. Для вероятностного
  агента это особенно опасно: без стандарта размещения он выбирает место для кода догадкой.
- **Механизм.** Прикладной код распределяется по слоям **Feature-Sliced Design** (ADR 0065)
  с каноническими именами `shared`, `entities`, `features`, `widgets`; роль app/pages
  исполняет существующий `src/app` (App Router), отдельный слой `pages` намеренно не вводится.
  Импорт разрешён только вниз по иерархии — вышестоящий слой вправе зависеть от нижестоящего,
  но не наоборот; слайсы одного слоя изолированы; каждый слайс доступен лишь через публичный
  `index.ts`. Направление и изоляция — это **гейт**, а не договорённость: Steiger
  (`check:fsd`, ADR 0066), ограниченный этими слоями, отвергает в CI любой импорт вверх,
  обращение между слайсами и обход публичного API; границу `src/components/**` при этом
  продолжает держать dependency-cruiser (ADR 0060) на непересекающейся области. Размещение
  нового кода определяется детерминированным деревом решений (навык `new-slice`), а не
  выбором агента. FSD добавлен **аддитивно**: примитивный kit `src/components/ui`,
  governance-артефакты `src/design-system` и инфраструктура `src/lib` / `src/i18n` не
  переносятся и остаются вне FSD-области. Пара ADR 0065/0066 пока в статусе `proposed` —
  ожидает человеческого гейта принятия.
- **Преимущество.** У агента всегда есть детерминированный ответ на вопрос «куда положить
  код», а прикладная архитектура не может бесконтрольно разрастаться: межфичевая связанность,
  импорт маршрута из UI и циклы превращают сборку в красную, а не всплывают (или нет) на
  ручном ревью.

### 2.11. Скрытая деградация со временем → самоактивирующаяся, реактивно растущая инфраструктура

- **Проблема.** Правило незаметно отключают, зависимость удаляют, конвенцию размывают
  десятком мелких PR — и ни один отдельный diff не является причиной.
- **Механизм.** При пустом каталоге `src/components/**` governance-гейтам пока не на чем
  срабатывать, и они автоматически активируются на первом добавленном компоненте. Правила
  развиваются _реактивно_: «Журнал дефектов» (Defect Log) фиксирует каждое недостающее или
  неоднозначное правило, а соответствующий инвариант проходит путь от прозы к проверяемой
  ревью Confirmation и далее к исполняемому гейту при первом же нарушении (ADR 0064).
  Плановый аудит дрейфа (ADR 0054) сверяет код с разделами Confirmation каждого принятого
  ADR и выявляет медленную эрозию — незаметно отключённый гейт или удалённую зависимость.
- **Преимущество.** Инфраструктура не остаётся статичной и не деградирует незаметно, а
  развивается управляемо, отталкиваясь от реально наблюдаемых дефектов.

## 3. Таксономия отказов дизайн-системы (P1–P9)

Governance-слой (ADR 0058–0064) существует против конкретных режимов отказа (P1–P9).
Источник — [`docs/design-system-ai-tooling-plan.md`](../design-system-ai-tooling-plan.md),
§2.

| P#     | Проблема                                                               | Основной слой                      | Чем закрыта                                    |
| ------ | ---------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| **P1** | Нарушения токен-правил (сырое значение; примитив вместо семантики)     | детерминированный                  | токен-линты; `check:tokens`, ADR 0058          |
| **P2** | Структурное дублирование компонентов (изоморфная композиция)           | структурный                        | композиционный граф + `ds:signature`; ADR 0059 |
| **P3** | Дублирование замысла (одна usage-role на разных компонентах)           | судейский                          | гейт коллизий; ADR 0061                        |
| **P4** | Галлюцинация агента при выводе/утверждении API                         | детерминированный (доказательство) | Figma-артефакт утверждения; ADR 0062/0063      |
| **P5** | Утечка композиционных требований в примитив (потеря переиспользования) | детерм. + структурный              | гейт границ; ADR 0058/0060                     |
| **P6** | Расхождение правил агента с CI («отмывание знаний»)                    | детерминированный                  | single-source кодоген; test-the-test; ADR 0058 |
| **P7** | Потеря контекста при возврате к компоненту в пакетном проходе          | судейский/процесс                  | Defect Log; пакетные утверждения               |
| **P8** | Неполное покрытие состояний (empty/overflow/loading пропущены)         | структурный                        | реестр архетипов + `ds:states`; ADR 0061       |
| **P9** | Дрейф сохранённых артефактов от живых источников после утверждения     | детерминированный                  | reconciliation-фитнес-функции; ADR 0063/0064   |

Показательно, что проблема сама диктует _слой_: то, что можно проверить точно (P1, P6, P9),
переходит в блокирующие гейты; то, что касается _полноты_ (P2, P8), — в структурные
подсказки; а неустранимо субъективное (P3, P7) остаётся за человеком.

## 4. Что было бы без этого подхода (контраст)

| Без подхода                                                  | С этим подходом                                       |
| ------------------------------------------------------------ | ----------------------------------------------------- |
| «Почему так?»: восстановление по истории git и опрос команды | `ADR 0013` — точный адрес мотивации                   |
| Конвенции в README, которые никто не гарантирует             | проверки `check:*`, явно сообщающие об ошибке         |
| Агент читает одно, CI требует другое                         | один проход `gen:*`: общий источник и проверка дрейфа |
| Гейт, незаметно переставший работать                         | `check:gates` требует отвержения нарушителя           |
| Медленная эрозия правил незаметна                            | аудит дрейфа против Confirmation каждого ADR          |
| Утечка ключа, уязвимость, лицензия — на усмотрение ревьюера  | механические сканеры в CI                             |
| ИИ пропускает `empty` / `loading`                            | покрытие вычитанием; молчание считается провалом      |
| Необратимое действие на скорости ИИ                          | перечень действий только для человека                 |

## 6. Одной фразой

Подход берёт самую рискованную точку современной разработки — **вероятностного исполнителя,
действующего быстро и необратимо** — и делает её безопасной, не жертвуя скоростью: каждое
правило машинно-проверяемо, выведено из единственного источника и доказанно самоисполняемо,
а за человеком остаются ровно те решения, которые нельзя свести к скрипту. Все преимущества
шаблона — прямые следствия этого: прослеживаемая история решений, проверяемые правила вместо
прозы, безопасность внутри гейтов и согласованность, которую не нужно каждый раз
подтверждать ручным ревью.

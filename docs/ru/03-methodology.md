# Методология разработки

> Как ведётся работа в этом репозитории: принцип «сначала решения», роли человека и
> агента, ветвление, цикл создания компонента, дисциплина состояния и три контура обратной
> связи, которые не дают правилам устаревать.

Методология не сводится к Agile или водопадной модели. Это **decisions-first разработка с
ИИ-агентом в роли основного исполнителя под детерминированным контролем**. Механизмы,
которые это обеспечивают, описаны в [02 — Защитные механизмы](02-defense-mechanisms.md);
здесь рассматриваются _процесс_ и _роли_.

---

## 1. Главный принцип: сначала решение, потом код

> Ничто не попадает в код без покрывающего решения. Правило, которому подчиняется агент,
> _начинается_ как ратифицированная человеком запись.

Когда изменению требуется решение, не покрытое ни одним ADR:

```
Нужно правило, которого нет в ADR
        │
        ▼
 Это внешний клиентский мандат? ──да──► строка CON-00x в constraints.md
        │ нет                              (файл только для человека)
        ▼
 навык adr → NNNN-*.md, статус: proposed (полный шаблон MADR)
        │
        ▼
 app.adr-review · adr-conformance-reviewer  (валидация шаблона + целостности корпуса)
        │
        ▼
 adr.py accept NNNN  ◄── 👤 ШЛЮЗ ТОЛЬКО ДЛЯ ЧЕЛОВЕКА
        │
        ├──► Реализация: агент подчиняется записи
        └──► adr-sync-claude-md: регенерация CLAUDE.md из принятого корпуса
```

Что делает процесс детерминированным, а не основанным на доверии:

- **Неизменяемость.** Принятый ADR **никогда не правится на месте** — только новая
  _замещающая_ запись с парными ссылками (`adr.py supersede`). PreToolUse-хук физически
  блокирует правку принятого ADR.
- **Целостность корпуса как самостоятельная проверка.** `adr.py lint` проверяет нумерацию
  (уникальную, без пропусков), перекрёстные ссылки, обязательные секции MADR, отсутствие
  незаполненных `{placeholder}`, словарь статусов и соответствие сгенерированного индекса
  `README.md` содержимому на диске.
- **Инструкция агента сгенерирована.** [`CLAUDE.md`](../../CLAUDE.md) регенерируется из
  _принятого_ корпуса навыком `adr-sync-claude-md` и не поддерживается вручную, поэтому не
  расходится с решениями.
- **Принятие выполняет только человек.** Агент может подготовить черновик и провести его
  рецензию, но никогда не устанавливает `status: accepted`. Это первый человеческий шлюз.

### ADR vs Constraint

ADR фиксирует _обдуманный выбор_ (не менее двух рассмотренных вариантов, раздел «Pros and
Cons»). Внешне заданный мандат без альтернатив (React, Next.js, набор MCP) — это не
решение, а **ограничение**: строка `CON-00x` в
[`constraints.md`](../decisions/constraints.md), на которую ADR _ссылаются_ по
идентификатору, а не пересматривают её.

## 2. Роли: ИИ-агент реализует, человек принимает решения

Модель ролей зафиксирована (ADR 0046/0047):

- **ИИ-агент — основной исполнитель.** Пишет большую часть кода под машинно-проверяемыми
  правилами. Атрибуция коммитов и PR оставлена потребляющему проекту и не навязывается
  шаблоном.
- **Совещательный ИИ — первый проход, а не замена.** Задания из
  [`scripts/ai/`](../../scripts/ai): ревью PR (0048), триаж сбоев CI (0049), черновик
  changelog (0050), обзор безопасности Layer 2 (0056), триаж обновлений зависимостей
  (0057). Каждое цитирует ADR-номера и **никогда не является обязательной проверкой**. Все
  инертны, пока человек не предоставит `AI_API_KEY`.
- **Человек — судейский слой.** Каждый PR (от агента или человека) требует не менее одного
  одобрения человека, отличного от автора, со сбросом устаревших одобрений при новых push.

Полный перечень действий, закреплённых за человеком, — в
[02 — Защитные механизмы, §9](02-defense-mechanisms.md).

## 3. Ветвление и поставка

Git-flow-lite (ADR 0011): **функциональные ветки → `dev` (интеграция) → `main`
(production, всегда готова к развёртыванию)**. Обе целевые ветки защищены, CI-проверка
обязательна. Production развёртывается из `main`; каждый PR получает preview-URL на Vercel
(ADR 0009).

- **Conventional Commits** обязательны (commitlint, `check:commits`, ADR 0072) — история
  пригодна для машинной обработки, и на её основе ИИ составляет черновик changelog при
  релизе `dev → main` (ADR 0050).
- **Развёртывание не входит в задачи CI.** CI отвечает за качество; сборку preview и
  production выполняет Vercel по git-интеграции.

## 4. Цикл создания компонента

Дизайн-система — наиболее регламентированная часть методологии. Порядок шагов (ADR
0058–0064):

```
ds:signature        ── ДО создания: проверка структурного дубликата по графу (P2)
        │
        ▼
design-intent.ts    ── на Definition-of-Ready: API выведен из usedIn (не угадан),
        │              граница slot-vs-variant с обоснованием
        ▼
ds:states           ── обязательный набор состояний архетипа; покрытие ВЫЧИТАНИЕМ (P8)
        │
        ▼
реализация + stories ── CSF 3; интерактивные компоненты требуют play-функций;
        │              истории = тесты (Storybook 10 + Vitest browser-mode)
        ▼
check:design-system ── ДО коммита: токены, границы, граф, intent, seals, i18n, gates
        │
        ▼
ds:escalations      ── перед ревью: коллизии usageRole, отклонения состояний,
                       доля автоматических одобрений для человеческих шлюзов (P3/P8)
```

Принципы этого цикла:

- **Покрытие вычитанием.** Отсчёт идёт от полного обязательного набора состояний архетипа,
  и каждое пропущенное состояние требует обоснования: `applicable: false` без `rationale`
  представляет собой замаскированный пропуск и отвергается. Молчание не равнозначно зачёту.
- **API выводится из использования**, а не назначается произвольно: контракт компонента —
  объединение всех требований `usedIn`; `check:design-intent` сверяет его с реальными осями
  cva/union.
- **Разрешённые токены — только сгенерированный список** `tokens.agent-rules.md`; токены не
  перечисляются в прозе повторно.
- **Истории — это тесты.** Покрытие из историй в browser-mode входит в единый порог ≥ 80 %.
  Чисто презентационные компоненты освобождены от play-функций, интерактивные — нет.

## 5. Архитектура приложения: Feature-Sliced Design

Компонентный слой стандартизирован глубоко, а у прикладного — где живут доступ к данным,
состояние и UI фичи и страница, что их связывает, — отдельного стандарта не было: код
нарастал бы под `src/app` и `src/lib`, а направление импортов не проверялось бы ничем. На
масштабе это даёт энтропию — межфичевую связанность, импорт маршрута из UI, циклы, — не
ловимую ревью. Против неё принят **Feature-Sliced Design** (ADR 0065, статус `proposed`).

Прикладной код распределяется по слоям с каноническими именами `shared`, `entities`,
`features`, `widgets`; роль app/pages исполняет существующий `src/app` (App Router) —
отдельный слой `pages` намеренно не вводится. Импорт разрешён только вниз по иерархии,
слайсы одного слоя изолированы, каждый слайс доступен через публичный `index.ts`.
Направление и изоляция — гейт, а не договорённость: Steiger (`check:fsd`, ADR 0066),
ограниченный этими слоями, отвергает в CI импорт вверх, обращение между слайсами и обход
публичного API; границу `src/components/**` держит dependency-cruiser (ADR 0060) на
непересекающейся области.

- Размещение нового кода определяется детерминированным деревом решений (навык `new-slice`),
  а не выбирается произвольно.
- Переиспользуемый shadcn-примитив помещается в `src/components/ui` (kit вне FSD) через
  навык `new-component`.
- FSD добавлен аддитивно: примитивный kit, governance-артефакты `src/design-system` и
  инфраструктура `src/lib` / `src/i18n` не переносятся и остаются вне FSD-области.

## 6. Дисциплина состояния: три непересекающиеся категории

Каждый элемент клиентского состояния имеет ровно одно место хранения; его размещение в
неверной категории — именно та ошибка, против которой существует эта модель (ADR
0025/0026/0027):

| Категория               | Где хранится        | Что хранит                                                                                                                               | Не предназначена для                             |
| ----------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Серверное состояние** | TanStack Query      | всё, что загружается из БД или записывается в неё — сущности, списки, любые данные, способные устареть                                   | UI-переключатели, URL-состояние                  |
| **URL-состояние**       | nuqs + typed routes | разделяемое и сохраняемое в закладках состояние, переживающее перезагрузку и переходы назад/вперёд — поиск, фильтры, сортировка, вкладка | секреты, крупные данные, эфемерные переключатели |
| **Эфемерный UI**        | Zustand             | переходное клиентское состояние — открытость выдвижной панели или диалога, текущий шаг мастера                                           | всё серверное или принадлежащее URL              |

Жёсткие правила: серверные данные **никогда не дублируются в Zustand**; оптимистичное
состояние хранится в кэше Query, а не в Zustand; Server Components **не импортируют стор**.
Оптимистичный UI — паттерн мутации _по умолчанию_ (`onMutate` → откат при ошибке →
инвалидация); неоптимистичная мутация требует объективной причины, обоснованной в ревью.

## 7. Валидация и окружение: единый авторитет

- **Zod — единственный авторитет валидации** (ADR 0017). Типы выводятся из схем
  (`z.infer`), а не описываются отдельно; ручной интерфейс, дублирующий схему, считается
  дефектом ревью. Каждая граничная схема несёт origin-маркер (`[env]`, `[form:signup]`, …).
- Одна и та же схема валидирует данные на клиенте и **повторно проверяет их на сервере**
  (ADR 0020), поскольку эндпоинт Server Action доступен в обход формы.
- **Окружение читается через два модуля**, а не через `process.env` напрямую:
  [`src/lib/env.ts`](../../src/lib/env.ts) (публичные `NEXT_PUBLIC_*`) и
  [`src/lib/env.server.ts`](../../src/lib/env.server.ts) (секреты за `server-only`-забором;
  их импорт в клиентский код _приводит к ошибке сборки_). Оба модуля проверяются немедленно
  при импорте (ADR 0018).

## 8. Доступ к данным: RLS как граница

Доступ осуществляется через request-scoped клиенты `@supabase/ssr`; весь пользовательский
доступ выполняется **от имени пользователя под RLS** (`auth.uid()`). Изоляцию строк
обеспечивает Postgres, а не `where`-условия приложения (ADR 0013). Миграции — обычный SQL
(включая RLS-политики) под `supabase/` (ADR 0014); после каждой миграции выполняется
`gen:types`, и CI завершается ошибкой при дрейфе (ADR 0015). Service-role ключ (обход RLS)
находится только за `server-only`-забором и никогда не достигает клиента. Навык
`create-migration` и агент `supabase-rls-reviewer` проверяют политику до PR.

## 9. Три контура обратной связи (защита от деградации)

Правила не задаются раз и навсегда — они развиваются на основе наблюдаемых дефектов:

1. **Цикл правки (секунды).** PostToolUse-хуки показывают результат lint и проверки дрейфа
   в момент записи, и агент исправляется немедленно.
2. **Реактивный рост (за волну).** [Defect Log](../design-system/defect-log.md) фиксирует
   каждое _недостающее или неоднозначное_ правило (не каждую ошибку). Инвариант проходит
   путь **проза → проверяемая ревью Confirmation → исполняемый Stage-1-гейт при первом
   нарушении** (ADR 0064). Детерминированный слой формируется из реальных дефектов.
3. **Аудит дрейфа (плановый).** ИИ сверяет раздел Confirmation каждого принятого ADR с
   реальным состоянием репозитория и докладывает `confirmed / drifted / unverifiable`.
   Решение принимает человек: исправить код или открыть замещающий ADR (ADR 0054).

> Это и есть «эволюционная архитектура»: набор фитнес-функций не статичен, а **пополняется
> реактивно** — каждый новый класс отказа, единожды проявившись, получает собственный гейт.

## 10. Управляемые отклонения (lean bootstrap)

Методология допускает _временные_ отклонения от принятого ADR, но только явно и под учётом.
Пока в шаблоне нет продуктового кода, тяжёлые наборы — Playwright e2e с воспроизведением
миграций и Storybook test-runner smoke — выполняются **локально**, а не в CI, ради
скорости. Каждое отклонение зафиксировано в
[`docs/bootstrap-plan.md`](../bootstrap-plan.md) с конкретным условием возврата (до первого
промоута `dev → main`) и **не является** изменением ADR: записанное решение остаётся целевым
состоянием.

> Правило: отклонение допустимо, только если оно (а) отступает от _принятого_ ADR, (б)
> временно и (в) называет конкретный триггер возврата. Постоянное изменение требует
> замещающего ADR.

## Методология одной схемой

```
Решение (ADR/CON) ──► генерация (CLAUDE.md, токены, типы) ──► машинный гейт
     ▲                                                            │
     │                                                            ▼
  человек                                                  агент реализует
  принимает                                                под правилами
     ▲                                                            │
     └──────── Defect Log / аудит дрейфа ◄── обратная связь ◄─────┘
              (правила растут из дефектов)
```
